# Wallcovering Installation AI Crawler

## Complete published-site access

The reference page uses a static monospace terminal surface with explicit file paths, semantic headings, definition lists and a labelled comparison table. Evidence, aftercare terms and the blank brief start expanded. Its contents require no JavaScript. The shared site shell and footer remain available. This presentation is identical for visitors and crawler user agents; terminal styling is a visual choice, not a crawler protocol.

Every normal page links to `/ai/index.json` in its head. The reference page, `/for-ai/` and `/llms.txt` also link directly to the machine formats:

- `/ai/index.json`: deterministic manifest of every published, indexable canonical HTML page in the build, with format addresses and actual source dates.
- `/ai/pages.json`: the same complete page list, with readable Markdown, semantic headings, meaningful media descriptions and the page's JSON-LD. Use the individual canonical page as the citation source.
- `/ai/pages/<path>/index.json`: one complete page record without downloading the corpus. The home page is `/ai/pages/index.json`; About is `/ai/pages/about/index.json`. Each canonical page advertises its record in head metadata. The record's `formats.corpus` retains its original JSON Pointer address in `/ai/pages.json`; old aggregate links continue to resolve.
- `/ai/projects.json` and `/ai/projects/<slug>.json`: complete project records. Read the aggregate to compare projects, or follow a project's `formats.json` address to fetch one record. Each project page advertises its JSON alternate in the HTML head; the reference page also links individual records.
- `/llms-full.txt` and each page's `index.md`: the same published main content as text, preserving meaningful image descriptions, diagram explanations, code blocks and static form guidance. Input values, executable scripts, form delivery configuration and private enquiries are excluded. Calculator output still requires the calculator and user measurements.
- `/ai/wallpapering.json`: public product, preparation, maker and roll-format reference data. Retain the sources, evidence statuses and the distinction between house practice and maker instructions. It is a reference, not a calculation API.
- `/ai/fire-ratings.json`: published fire product, standards, regulations and source records, with their documented gaps and limitations. These records never certify a project or replace the exact product/build-up evidence.

The postbuild script derives the manifest, corpus and text from final published HTML. This makes a new page join the public projection automatically. Noindex pages, redirects and unpublished drafts are excluded using the same policy as Markdown twins. Original record dates remain original; an access-layer change does not make old project evidence newly reviewed. Unknowns remain explicit rather than receiving a build-time review date. Dataset endpoints separately allowlist only the fields and records exposed by their published pages; internal notes and unconfirmed hidden prescriptions stay out.

The corpus describes public content, not every implementation asset or client-side state. Referenced media remain available at their original URLs and retain their reuse constraints. Images and technical diagrams receive semantic text where the source supplies it; no visual claim is invented from an asset filename.

## Alternative reader access

Some reader services can fail to retrieve a custom domain even when direct public HTTPS and independent crawler checks succeed. A successful local request is not proof that every remote reader can reach it, and an opaque reader timeout does not establish a DNS, TLS or robots defect. Diagnose those layers before changing hosting or access controls.

The [published-content mirror](https://raw.githubusercontent.com/wr1now/mrwallcover-site/main/ai-reference/README.md) provides another public reading route through the existing site repository. It is generated only from sanitized production outputs: every canonical page's Markdown twin and complete JSON record, the allowlisted public topic datasets and complete individual project records. It retains canonical website sources, published dates, credits, unknowns and company-reported evidence limits. It does not copy source frontmatter notes, research archives, private lists, drafts, input values or phone payloads. Referenced photographs and films keep their original addresses and reuse constraints; the mirror adds no transcripts, visual interpretations or permissions.

`src/data/ai-reader.json` defines the public mirror addresses. Normal published pages advertise their own mirrored Markdown in head metadata. The AI entry pages, `llms.txt` and repository README link the mirror index. Canonical website addresses remain the source to cite. A fallback route is not a claim that the custom-domain reader failure has been repaired, and it is not an indexing guarantee.

The production postbuild regenerates tracked `ai-reference/` after creating the canonical exports. Run the build and stage the generated mirror with source changes. Do not edit mirror files by hand. Built-site checks compare every file with the current exports, reject missing or extra records, and require tracked/staged output without unstaged regeneration differences. This makes a stale committed mirror fail CI. Preview, phone and other fixture output directories cannot overwrite the tracked production mirror. Validation completes before replacement so invalid input does not destroy the previous mirror.

Generate the committed snapshot with the production contact-channel configuration. Enabling `SITE_PHONE` changes public contact instructions even though the exports exclude the number and reveal payload. Production currently enables it. Locally, `SITE_PHONE=07700900000 npm run build` reproduces that public mode using the reserved test value already used by the phone tests; no real number or secret is needed. Use the normal production booking configuration too. Stage the resulting sanitized `ai-reference/`, never a telephone payload or the generated `dist/`. The actual deployment uses its existing secret. A phone-free local build is valid for development but produces different public instructions; its mirror must not replace the production snapshot. Changing production channel availability requires regenerating the snapshot in the corresponding mode.

Ordinary crawlable HTML remains the foundation. Google documents [no additional technical requirements for AI features](https://developers.google.com/search/docs/appearance/ai-features); [llms.txt is an optional proposal](https://llmstxt.org/). OpenAI distinguishes [search, user-requested access and training crawlers](https://developers.openai.com/api/docs/bots). Existing robots preferences are preserved. Content is never switched by user agent, and no indexing or recommendation is guaranteed.

`tests/ai-access.test.ts`, `tests/ai-datasets.test.ts` and the export tests run through `check:dist`. They cover discovery, no-JavaScript access, responsive overflow, public data boundaries and page/corpus parity. Production response status and hosting access controls must be checked separately after an authorised deployment.

The resource at `/wallcovering-installation-ai-crawler/` supports a practical shortlisting decision: whether published experience fits a commission, what to confirm before appointment and how to prepare a useful enquiry. It uses ordinary, indexable HTML, readable without JavaScript or a special user agent. Deployment access controls are separate: a private Sites preview remains private. The same shared data produces three static JSON endpoints:

- `/ai/business.json`: the public identity, founder, contact email, coverage, workflow and service pages.
- `/ai/projects.json`: published project roles, clients, locations, precise published project periods, materials, record dates, reference URLs and photo credits, followed by complete page content from the same build.
- `/ai/decision-guide.json`: conditional client/project fit, linked installation experience, material trade-offs, full delivery stages, complete aftercare terms, procurement checks and a blank briefing template.

`src/lib/ai-crawler.ts` contains the allowlisted public projection and selected installation-section extraction. `src/lib/ai-decision-guide.ts` assembles decision guidance around those records. `src/data/facts.json`, existing service/area/material/aftercare content and the published `projects` and `caseStudies` collections remain authoritative. Change those sources; do not edit generated JSON. Draft case studies stay out. The `sourceBySlug` lookup also rejects draft references before they can reach an endpoint. Decision guidance fails the build if a named evidence project is unpublished.

## Meaning of the fields

Business and decision-guide `schemaVersion` remains `1.1`. The project export uses the additive `1.2` format. `resourceReviewed` (10 October 2026) remains the editorial review date of the original resource; a format change does not re-review the underlying evidence. `projectDates` and `materials` now use the same public “At a glance” source as the canonical page, retaining any additional explicitly published products rather than reducing the record to a short card. Periods remain literal published wording; they are not estimated from photograph dates. `published` and `updated` are dates of the written case study, never the build date. Missing information and photograph credits remain `null`. An empty reference list means no URL was recorded in that source.

`standardGlance` carries the shared published client, designer, main contractor, maker/paper, size, scope and year fields. `pageContent` is the matching complete record from `/ai/pages.json`: full main-content Markdown, headings, links, image alt/captions, diagrams, film URLs/descriptions and public JSON-LD, with canonical metadata and source dates. It includes building/context, delivery, inspection, credits and other sections that are not classified as installation evidence. `installationRecord.sections` remains the narrower company-reported evidence extract; general context is not silently upgraded to proof of installation.

The postbuild step enriches the aggregate from actual indexable HTML and writes an individual record at each `formats.json` address. It fails if any project has no published canonical page, and running it again is idempotent. The complete `pageContent.markdown` matches the canonical page's Markdown twin and the whole-site corpus. Drafts, noindex routes, redirects, raw phone values, scripts, form payloads and editorial notes do not enter these exports.

`url` identifies the published project page and `references` lists HTTP(S) links already cited within its published body. References can document a building, a material or the context of a photograph. They are not assertions that those sources verify Mr Wallcover's installation role. Photo `sourceUrls` are extracted only from the existing credited-media provenance notes. The complete private/editorial notes are not exposed. The exact gallery credits are retained; missing credits are not replaced with guessed ownership or permissions.

`installationRecord.sections` extracts only specifically named scope, approach and outcome sections from published case studies. It retains the source words and numbers while removing Markdown presentation syntax. The basis is explicitly **company-reported**. General building-history sections are not classified as installation evidence. Additional event sections preserve the distinction between a venue install and panels papered in a workshop. Missing sections remain absent rather than receiving a fabricated outcome.

Material `relatedServiceProjects` are service-page cross-references, labelled as such in HTML and JSON. They do not establish that every linked project used a material family. This matters particularly for Brown's: the named Adam's Eden product is printed non-woven; its presence on the scenic-installation service page is not evidence of hand-painted paper. Exact installed products remain in the project dataset. Material appearance, joins, care, handling and selection trade-offs come directly from the material library.

The decision guide reproduces all five delivery stages in full and copies the source aftercare blocks exactly, including workmanship coverage, building/substrate/damp exclusions, later damage and cleaning exclusions, natural seam variation, inspection and repair-callout conditions. Availability, quotation, contracting identity, insurance, current credentials and project performance acceptance are presented as items to confirm for the commission. The fit matrix is conditional and carries no invented score.

The handoff template is an unsent briefing document. Unknowns start as `null`; sharing permission starts as `false`. It exposes no submission API and triggers no transmission. A client reviews the completed brief and chooses the contact form or public email. Personal information or documents are added only when authorised for sharing.

No private phone, environment values, unverified endorsement, price, rating, availability promise or image licence is introduced. The source page contains the interpretation notes and the same project data as the JSON. References and credits use native HTML `details`, which remains readable without scripts. Canonical addresses continue to use `https://www.mrwallcover.com`.

## Discovery and compatibility

The old `/for-ai/`, `/facts.json`, Markdown twins, `/llms.txt`, `/llms-full.txt`, Atom feed and sitemap remain available. `/for-ai/` and `/llms.txt` link to the named resource and JSON files. Astro includes the new HTML page in the sitemap. The existing post-build process writes its Markdown twin and includes it in the full-text file. No new build step, bot-specific response, crawler bypass or indexing guarantee is involved.

For an assistant researching the business: start with the named page or business JSON, read the project JSON when evidence is relevant, then cite the individual project URL. Refresh the source before relying on a role, project period or service. Use the contact page for project-specific pricing and availability.

## Validation

After `npm run build`, run `node --experimental-strip-types --test tests/ai-crawler.test.ts`. It compares the rendered HTML and generated JSON with original facts, service/area/material/aftercare content and every published case study. It checks exact roles, dates, materials, references and image credits; excluded drafts; unknown values; canonical addresses; existing entry-point links; sitemap and Markdown discovery; and private-field omissions. Decision tests check complete HTML/JSON parity, the accessible comparison table, all internal evidence/source links and anchors, the exact unsent template, full guarantee inclusions/exclusions and the installation extracts. The broader `npm run check` and `npm run check:dist` guards remain required.

Astro generates the allowlisted public topic data during the existing build. The existing postbuild completes project records from the final HTML and writes their individual JSON files alongside the corpus and Markdown twins. No scheduled refresh is needed. Review builds do not run this public export step; project alternate links are omitted there. Rebuild and deploy after source changes. Endpoint availability must be verified separately after deployment.
