# Mr Wallcover website

Read [README.md](README.md) before changing this Astro site.

Every new or substantially changed page must follow [the visual standard](docs/design/visual-standard.md) and use the shared layout and components. Use `Base.astro` for page chrome, `Action.astro` for new prominent actions, `Icon.astro` for the shared icon family and `Picture.astro` for registered photography. Improve shared templates before repeating local markup or CSS.

Assess whether relevant photography, a diagram or an icon helps visitors understand or navigate the content. Record the decision in [the page review](docs/design/page-review.md) and the PR; give a concrete reason when a text-only layout is appropriate. There is no image quota. Preserve image provenance, captions, credits and the distinction between an illustration and evidence of completed work. Do not invent commissions, endorsements or technical certification.

Add each new HTML route to [the route review](docs/design/route-review.json) with its specific visual decision. `check:dist` checks that this ledger covers every normal published and utility page, then opens each at mobile and desktop widths. Use the shared landing, guide, material and professional templates so new entries inherit their evidence, briefing and action patterns. Keep legal, factual and utility content text-led when imagery does not help.

Question rows use the shared `QuestionVisual.astro` policy. Keep substantial right-hand studies for questions about a physical material or detail; `dimensionalStudyHelps` makes generic calendar, folio and document questions typographic instead of repeating 3D clip art. A typographic row must not reserve an empty study rail. Reuse native FAQ/disclosure components and review the topic mapping for new questions. Keep buyer answers open and retain every answer, anchor and factual boundary. Static factual/utility routes keep their existing drawing policy.

Use shared `DesignObject.astro`, `DesignStudy.astro` and `ObjectMotionControls.astro` where a physical study explains the content. Preserve real project photography, the illustrative label, server-rendered WebP posters, lazy visible rendering, shared Pause motion and live OS/footer preferences. Useful open buyer/Guide studies use the container-aware 144px/192px/288px frames; phone answers remain full-width and long answers use the 44rem reading measure. Generic timing or paperwork does not require an object, and a photographic Guide card takes precedence over an illustration. Do not make every page invent its own renderer or motion controls.

Keep the homepage concise: the current composition has seven sections for hero, trust, selected hotels, Dorin, five stages, aftercare and one closing action. Move detailed material to the appropriate indexable Practice, Projects, Contact, FAQ or Materials page; never delete it to satisfy a length target. Preserve original prose, real photographs/films, credits, links and FAQ answers in published destinations, and update the relocation/preservation receipts. Shared navigation comes from `src/content/navigation.json`: six buyer links, with AI Crawler in the footer. Use the shared text roles: 18px reading text, 15px labels/controls/captions, and the existing serif display hierarchy. Booking controls say **Book a call** while retaining the twenty-minute destination/duration.

Makers cards use `MakerCardPhoto.astro` and the reviewed `maker-card-photography.json` mapping. Use an evidenced maker installation where available; otherwise caption a real Mr Wallcover craft example with its actual maker and site. A contextual example must never imply installation, affiliation or supply of the directory brand. Preserve registered image rights, credits, stage labels and evidence links. New profiles need the same evidence decision, not an invented match or an image quota.

Reuse `editorial-layout.css` and the appropriate family composition for section navigation, readable articles, aligned facts/briefing/evidence rails, contained reference tables and credits kept beside their photographs. Preserve every published paragraph, heading, answer, destination and evidence boundary when reorganising data. `Base.astro` supplies the shared ivory-linen and botanical atmosphere through `AtelierAtmosphere.astro`: a visible but restrained woven ground, original plum blossom, small perched birds on branches and a discreet lower-right water-lily accent. Reuse its four active optimised WebP assets, masked and faded below content; do not add another page-specific background or renderer. At widths up to 767px show the woven linen only; hide the bird, blossom and pond layers so decoration does not sit behind phone reading. Desktop suitable pages retain restrained botanical motion after load, shared pause/reduced-effects and document-visibility handling. Factual/legal/reference utilities, including Makers and Buying routes, retain static linen/right-hand bird artwork and omit the plum/water-lily layers; noindex pages omit the whole atmosphere. Keep reading surfaces, controls and genuine photography above it. This original generated artwork is decorative, not a named maker's pattern, a photograph of installed silk/linen, an affiliation or project evidence; preserve the current provenance in `docs/design/plum-water-lilies/assets.md` and the retained linen/bird sources in `docs/design/linen-botanicals/assets.md`.

Preserve existing destinations, enquiry behaviour, accessibility, structured data and public content projections. Keep the shared footer on new routes. Include responsive screenshots and interaction checks proportionate to the change; passing builds do not establish visual quality. Keep verification status honest and list skipped checks with their reason.

This is a public website repository. Do not import private research archives, private exclusion lists, leads, credentials or unpublished claims. Draft publication requires the existing editorial review; design changes do not clear content blockers. Do not merge or deploy unless the user has authorised that action.

The production build generates the sanitized public reader mirror in `ai-reference/` from the same published HTML and exports. After changing public content, run the production build with the same public contact-channel configuration and stage the resulting mirror changes with the source. A reserved phone-test value can reproduce phone-enabled public copy locally without access to the real secret; see `docs/ai-crawler.md`. Do not edit generated mirror files by hand or copy raw research into them. Built-site checks reject missing, extra or stale mirror files; preview and fixture builds must not overwrite this public mirror.
